# 複雑な案件を図解する

実装や資料を根拠に、「誰が、何をすると、どこで何が起き、何が返るか」を読む人が追える図解へ変換する。技術名を消さず、同じ枠の中に役割をやさしく添える。色や書体はそろえても、レイアウトは情報の関係に合わせて毎回設計する。

このスキルのフォルダを以下 `<skill>` と書く。ワークスペースでは `tools/skills/visualize-project-architecture`、案件へ写した場合はその写し。コマンドはワークスペース（または案件）のいちばん上で実行する。

図解は資料作りなので、頼まれたら設計を本人に見せて待たずに作ってよい。どの案件の図か・読む人・置き場が決まらない時だけ 1 問で聞く。作った図や分かったことは案件の Wiki（`wiki/projects/<名前>.md`）へ残す。このフォルダは OS の更新で入れ替わるので、ここへ書き足さない。

## 成果物

案件の `projects/<案件>/visuals/` に作る。案件の無い単発の図なら `projects/<図の名前>/`。ワークスペースのいちばん上や `tools/` には作らない。同じ名前のファイルが既にあれば上書きせず、別の名前にするか聞く。

- `project-overview-evidence.md`: 図に載せた事実と根拠
- `project-overview-plan.md`: 読む人、伝える結論、選んだ図法、パネルの構成、使ったデザインの根拠
- `project-overview.html`: 図解の編集できる正本
- `project-overview.png`: 3840×2160 の共有用の画像

1枚で誤解なく説明できない場合は、概要を `project-overview.*` に保ち、`detail-{topic}.html` / `.png` を必要な分だけ足す。情報を削って1枚へ押し込まない。

## 手順

### 1. 調べる

1. 対象を決める。読む人の指定が無ければ「初めて聞く非エンジニア」にする。
2. 案件の Wiki・`AGENTS.md`・README・マニフェスト・設定・画面・入口の処理・保存の処理・外部との連携を、必要な範囲だけ読む。
3. 使う人の操作、処理の順番、保存先、外部サービス、公開の範囲、例外・終わりの条件を実装から追う。
4. `.env`・認証の JSON・鍵・トークン・個人のプロフィールは読まない。長いパス・秘密の値・公開しなくてよい識別子は図に載せない。
5. `project-overview-evidence.md` に「図の説明 / 確認した事実 / 根拠のファイル」を書く。推測は事実と分ける。
6. 図に描く矢印ごとに「起点 / 終点 / 動くもの / 根拠」を表にする。公開・閲覧・保存・削除など目的の違う流れを 1 本の物語に混ぜない。

### 2. 説明の設計を先に作る

`<skill>/references/diagram-strategy.md` と `<skill>/references/visual-style.md` を必ず読む。前者で情報の関係から図法を選び、後者で図の見た目の決まりを使う。

配色・書体・角丸・影の優先順位:

1. 本人が今回はっきり指定したこと、または見せてくれた参考の画像
2. 本人が了承して保存したデザインの設定（ワークスペースの `tools/design.md` の手順で決めたもの。案件・会社・個人の順に近いものを優先）
3. ワークスペースのいちばん上の `DESIGN.md`（標準テーマ）

会話だけに出た好みは再現の条件にしない。上位の指定を使う場合も、採用元を設計に書く。

`project-overview-plan.md` に書くこと:

- 読む人と、図を見た後に分かってほしい一文
- 主役になる人または処理
- 選んだ図法と、その図法が内容に合う理由
- 使うデザインとその根拠、主な色
- パネルの構成、主な箱、矢印の意味
- 実際の画面・アイコン・凡例を使うか
- 3840×2160 を半分の大きさで見た時にも残す情報と、省く細部
- 概要から外す情報と、必要なら詳細図へ移す理由

前回の図や例のレイアウトを既定にしない。内容が同じ関係を持つ場合だけ使い回す。

### 3. 図解の HTML を作る

`project-overview.html` を案件ごとに設計する。固定のカード数・サイドバー・用語集・流れの本数を前提にしない。

- 3840×2160 の 16:9 のキャンバスを使い、本文は画面の端から十分に離す。
- HTML / CSS / SVG で作り、文字を選べる状態を保つ。外部の CDN・Web フォント・ネットワークを使わない。
- CSS の文字の大きさは px で書く。最小 28px、ふつうの本文 32〜36px を下限にする。小さくしないと入らない情報は省くか詳細図へ移す。
- 矢印の向き・線の種類・色に意味を持たせ、凡例と食い違わせない。
- 技術名には「Cloudflare R2 — 共有ファイルを保存」のように役割を添える。
- 画面が理解の中心なら、確認した実際の画面か、簡単な画面の再現を主なパネルに使う。
- たとえやキャラクターで実物を置き換えない。宣伝の言葉、確かめていない性能の数字、存在しない AI の処理を足さない。
- 確かめていないこと、設定した後だけ成り立つこと、追加の条件が要ることは、その主張と同じ箱かすぐ下にはっきり書く。下の端の小さな注記だけで済ませない。
- 飾りより、視線の順番・まとまり・因果関係・主従を優先する。
- 決まった形にするのは配色・余白・角丸・線などの見た目の言葉で、情報の構造やレイアウトではない。

### 4. PNG に撮る

撮影の道具 `<skill>/scripts/shot.mjs` を使う（Node.js 18 以上、追加のパッケージ不要。Chrome・Edge・Chromium のどれかを、本人のプロファイルを使わない一時のプロファイルで裏側で動かす）。この道具が Chrome などの実行ファイルを一時のプロファイルで裏側に動かすのは、本人のブラウザを開くことには当たらない（本人の画面・設定・履歴・ログインには触れない）。一時のプロファイルは OS の一時フォルダに作られ、撮り終えると道具が消す。了承の要るワークスペースの外の変更には当たらないので、`TMPDIR` をワークスペースや案件の中へ向けない。撮影をほかの変換の道具（画像のライブラリなど）で代えない。28px の検査と縮小の確認はこの道具でしかできない。使い方は `node <skill>/scripts/shot.mjs --help`。

- 4K の正本 `project-overview.png`（3840×2160）と、同じ配置を縮小した確認用の画像（1920×1080。OS の一時フォルダに置く）を撮る:

```bash
node <skill>/scripts/shot.mjs single projects/<案件>/visuals/project-overview.html --out projects/<案件>/visuals/project-overview.png --preview {一時フォルダ}/project-overview-preview.png --min-font 28
```

- 28px 未満の文字があると道具が不合格にするので、文字を小さくせず構成を直す。直して撮り直す時は `--replace` を付ける（付けないと同じ名前の画像を上書きせずに止まる）。
- HTML が読むファイル（画像など）は、HTML と同じフォルダかその下に置く。外のフォルダを読むと不合格になる。
- 外部への通信やページのエラーがあると不合格になる。理由を直して撮り直す。
- 道具が「撮れていません（未確認）」で終わった時（ブラウザが見つからない等）は、PNG ができたと言わない。HTML は残し、未確認として報告する。ブラウザやソフトを勝手に入れない。
- 本人のブラウザ（既定のブラウザを含む）を `open` などで開いたり、画面操作の道具で動かしたりしない。

### 5. 意味と見た目を確かめる

4K の PNG と確認用の画像を、画像として実際に開いて見る。最低限:

- 3840×2160 で、文字切れ・重なり・画面の外へのはみ出しが無い
- 最初の 10 秒で「何の図で、何ができるか」が分かる
- 1920×1080 の確認用の画像で、主な説明だけでなく残した補足も読める
- 使う人の操作から結果まで、視線で追える
- すべての矢印が根拠の表の「起点 / 終点 / 動くもの」と合っている
- 読む人に必要な用語の説明が、その用語の近くにある
- 実装に無い機能、根拠の無い安全性、秘密の値、個人情報が無い
- 上位のデザイン指定が無い場合、`DESIGN.md` のオリーブ・クリーム・ラストオレンジが主な見た目になっている
- 中身の違うものを、同じ決まった形に無理に合わせていない

問題があれば、文字を小さくする前に構成・まとまり・図法を見直す。重要な情報が収まらなければ詳細図へ分ける。画像を見て直すのは最大 2 回。合格したら確認用の画像を消し、4 つの正本だけを残す。

### 6. 報告する

PNG、HTML、根拠の表の順に案内する。選んだ図法と「この図で分かること」を短く説明し、確かめていないことがあれば 1〜3 点に絞って書く。撮影できなかった時は、そのことを最初に書く。
