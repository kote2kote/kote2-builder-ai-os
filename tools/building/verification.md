# 検証と完了判定

完成と言う前、設定/スキル/共通手順を替えた時に読む。共通手順 `verification@1`。

1. **静的**: 新規標準案件では `python3 tools/building_check.py --project projects/<名前>`。出力に誤りがあれば直す。Python 3.11以上が必要。ファイル・設定の型/標準安全項目・入口・スキル一式を調べる。非標準の既存案件は同等性を別途点検する。
2. **実際の読込**: 各AIで案件を直接開き、共通指示と必要なスキル、実効権限が読めるか確認する。認証不能・未導入なら未確認で止め、代わりに成功したことにしない。ホストの設定は静的ファイルと別に記録する。
3. **成果物**: 設計で決めた自動試験と実操作を実行し、期待と実際を比較する。レシピは元成果物を読まず、架空値で再制作する。UIは広幅/狭幅で見る。試験の `auto` は無通信を意味しない。試験コードを先に読み、公開・課金・破壊・認証ファイル読取は承認範囲を確かめる。
4. **記録**: 案件/レシピの版、共通手順ID@版、環境/AI、実施日、操作/コマンド、期待/実際、証拠への相対リンク、未確認、本人の確認を残す。本人情報・秘密を証拠へ写さない。

案件AGENTSを作成/補修したら、案件Wiki・親OSのAGENTS・Wikiの読書き規則の3リンクを案件フォルダ基準で照合する。実AIの記録試験は別に、架空案件を直接開いて問題解決と判断を案件Wikiへ、横断知見を知識ページと分類/入口へ残せるか確認する。親Wikiに書けない条件では、権限を変えず未反映の保存先・理由・追記案を返すことも確認する。静的検査や別AIの成功でこの試験を代用せず、未実施なら未確認と記録する。

`build-contract.json`のchecksは人またはAIが書いた**実施記録**。道具は証拠ファイルの存在と形式を点検するだけで、試験成功を認定しない。空、unrun、failを含む記録は完了候補としない。全部passでも証拠と実ログを確認し、未読込のAIを対応済みにしない。

検査器を通すことは完成の十分条件ではない。公開/課金/破壊/権限変更は別の確認が要る。本人Wikiと案件を別々に保存し、保存した対象と復旧できない外部データも伝える。

対象AIが未導入なら、そのAIの読込試験は `unrun` のままにし、別AIの成功で代用しない。引き継ぎには「未確認のAI／案件を直接開く場所／実行する読込確認／期待する返答／まだ試していないこと」を短く示す。AIの新規導入やPC全体の設定変更は別の了承を得る。
