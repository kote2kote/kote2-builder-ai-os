# 古くなった方法を見直す

新規制作・レシピ再生・拡張・設定変更で、版の不一致、廃止の警告、公式例との食い違い、再現失敗、外部サービス/料金への依存が見つかった時に読む。共通手順 `freshness@1`。日付が古いだけで無効にしない。会話外の巡回・常駐監視・自動収集はしない。

## 調べて、候補を分け、試す

1. 使おうとしている手順/レシピのID・版と、食い違う箇所・影響を明示する。公式ドキュメントの該当ページを取得し、URL・取得日・対象版・確認できた事実を記録する。検索の要約だけで断定しない。資料が取得できないなら「資料未確認」で、推測の新設定を適用しない。
2. 旧方式がまだ有効なら併存させる。置換/別方式の候補を、対象環境・利点・互換性・戻し方とともに分ける。個人の試行は案件内の候補ファイルか個人Wikiへ。配布正本 `tools/building/` や旧レシピの `templates/core` を利用中に自己改造しない。
3. 設計の範囲内の非破壊試験だけを隔離した架空案件で行う。公開・課金・外部データ変更・秘密読取・権限緩和のために勝手に進まない。試験不合格や未実施なら候補のまま。本人の事実をAI判断でverifiedにしない。
4. 「資料確認」「静的検査」「各AI実読込」「再制作」「本人承認」を別々に記録する。新方式が動いても旧版の成功履歴を書き換えない。非互換なら新しい版か別IDにし、旧版と後継/代替のリンクを残す。
5. 関連レシピの依存手順ID@版を調べ、変わる手順に依存するものだけ「再確認が必要」にする。依存記録が無いレシピは「影響不明」で個別点検し、無関係/再制作済みと断定しない。既存レシピは [一覧のJSON](../recipes.md)で探索できるが、一覧の旧verifiedは依存解決の証拠ではない。

## 記録する形

案件の作り方メモまたは個人Wikiへ、`方法ID@旧版 → 候補版/別ID / 理由 / 公式URL・取得日・対象版 / 試験した版と環境 / 期待と実際 / 未確認 / 影響するレシピID@版 / 本人の了承 / 戻し方`を短く残す。レシピ側の検証記録にも使った方法ID@版を残す。

公式の共通手順へ反映したい改善は開発側への変更提案にする。利用者の配布正本は確認済みOS版の更新経路でのみ替える。本人のレシピは反映の了承を得て更新し、旧結果を保持する。これにより、個人の試行・採用と全利用者向けの更新を混ぜない。
