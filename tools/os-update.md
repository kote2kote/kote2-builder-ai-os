# OSの更新・取消・復旧

[READMEへ戻る](../README.md)

AI・点検担当者向け。コマンドとコード内のパスは、ワークスペースのルートを基準にします。

自動確認の通知・設定と、明示された更新・取消・復旧のときにこのページを読む。日常の挨拶で全内容の取得や更新診断は始めない。書込み前の中断確認は `wiki/README.md` の「保存前の安全確認」を使う。

## 利用時の自動確認

新規会話の最初と、長い会話を次の本人発言で再開したとき、信頼済み旧版で `python3 -I tools/release_package.py auto-status --ws .` を使います。案件だけで開いた場合も親OSのルートを確認し、コマンドと `--ws` はそのルートを指定します。子タスクでは実行せず、通信禁止・権限不足・親OS不明なら確認を省き、本題の仕事を続けます。アプリの起動イベントや発言のない間には動きません。常駐監視・スケジューラ・アプリ設定の変更は追加しません。

- 初回と、前回の確認試行から24時間以上たった場合だけ、公式identityと、既定branchのcommitに付いた公開tagを確認します。24時間未満は通信しません。通信に使う合計待ち時間は最大8秒で、Git取得・全内容検査・check/apply・カスタマイズの収集は行いません。
- JSONの `status: checked` は確認成功、`skipped` は間隔内・無効・別会話で確認中、`unknown` は未確認です。通知するのは `notify: true` のときだけ。同版・旧版なら無言で通常の仕事を続け、失敗も「更新なし」とは扱いません。失敗した試行も24時間待ち、繰返し通信や認証の催促をしません。保存自体ができない場合は通信せず未確認とします。
- 新しい版を見つけたら、本題への回答を優先し、末尾へ「OSの新しい版があります（旧版 → 新版）。更新はまだしていません。今の作業後に確認できます」と短く添えます。過去に通知した最高版より新しい版だけを通知し、公式側で版が巻き戻って再公開されても同じ版は再通知しません。通知対象の返却時に記録するため、返却直後に会話が中断すると未表示のまま再通知が抑制されることがあります。通知・全文取得・適用を一括承認しません。
- 新しい記録は `tools/.state/os-update/` に、試行時刻・通知済み版・有効/無効だけ保存します（形式番号を除く）。Git・配布対象外のOS内部状態で、本人用の道具置き場ではありません。旧ルートの `.builder-os-update/` だけが存在する場合はその記録を継続利用し、新設・自動移動・削除はしません。新旧両方が存在すれば競合として停止し、記録を確認します。本人情報・Wiki本文・認証情報を保存/送信しません。並行する会話はローカルlockで重複確認を避け、終了・異常終了でlockの占有はOSが解放します。時計が戻った場合は通信せず保留し、記録した時刻から24時間以上になるまで待ちます。すぐ知りたい場合は明示のstatusで確認できます。不正な記録やリンクは書き換えず未確認とします。
- 本人が自動確認を止めると言ったら `python3 -I tools/release_package.py auto-config --ws . --enabled off`、再開は `--enabled on` を使います。設定は通信せず、他のワークスペースへ波及しません。「あとで」は適用しないだけで、自動適用の予約は作りません。
- 「更新ある？」「更新して」と明示されたら、自動確認の間隔・無効設定・通知済み版にかかわらず、下の `status` で新たに確認します。あると即答した後、同じターンで固定commitの内容とカスタマイズを調べ、次のOKを待つ既存手順へ進みます。自動確認のキャッシュを適用判断に使いません。

## 明示された更新依頼

Claude共通設定のsandboxを環境別へ分離する更新では、適用前の説明で「共通のRead/Edit deny・危険Git deny・push/publish askは保持するが、sandboxなしではBash等の別経路を隔離しない」ことを明示する。隔離を続ける利用者には、親/案件のlocal設定へ移す案を [設定手順](building/settings.md) に沿って提示する。既存のlocal・user・管理者設定を勝手に変更しない。旧版checkの「保持・未点検」のキー一覧だけで実際の保持を判断せず、変更前と適用予定の設定差分を照合する。sandbox独自変更の競合は上書きせず停止する。既存案件の設定は通常OS更新の対象外であり、親だけの更新を案件も修正済みと扱わない。次のOKと本人確認の窓は従来どおり。

「OSアップデートして」「OSの更新ある？」は、まず更新の有無と内容を調べる依頼です。最初の「更新して」を適用の承認にしません。利用中の版と信頼済み旧版検証器の公式anchorを読み取り、下のstatusで公式GitHubの公開tagだけを確認します。**全treeを取得する前に、必ず本人へ素早く「更新あり／なし」を応答します。** 通信・取得・検査のどれかが失敗したら「未確認」と伝え、「なし」とは答えません。そのときの進め方は下の「確認・取得ができないとき」。anchor未設定やこの取得方式に未対応の旧版は、初回移行の案内へ進みます。

更新があると伝えた場合は、その返答だけでターンを終えず、同じターンでstatusのfull commitに固定してfetch・旧版checkへ進み、内容を調べて続けて答えます。公開の記録（注釈つきの公開tag `vX.Y.Z`）が付いていないcommitは、既定branchにあっても取得しません（未確認として扱います）。Releaseの発行やattestationは必須にしません。取得・検査の失敗をローカルコピーや新版ツールの先行実行で回避しません。

**版を飛ばした更新**: 何版か飛ばしていても、途中の版を順に入れ直さず、最新へ1回で更新します。公開前に、公開済みの各版の導入済み道具から最新へ直接更新できることを確かめています。導入済みの取得器が最新を拒否する旧配置の版（4.3.0以前）だけは、移行準備版を1回通ります（下の「4.3.0以前から公式配置版への移行」）。その場合、本人に依頼を言い直してもらわず、導入後に同じ依頼の続きとして最新を確認します。段階ごとに差分・保全案の説明、本人のOK、確認窓を通します。後の段階の差分は前の段階の導入後にしか確かめられないので、前の段階のOKで後の段階まで承認したことにしません。

旧版 `update_os.py check` の差分から、変更内容と利用者カスタマイズへの影響を調べます。利用者が追加・変更したスクリプトや設定を、単に標準版へ上書きして消してはいけません。独自ファイルへ分離する案や差分を統合する案など、**今ある内容を残して新OSへ追従する方法**を現行checkと手順の範囲で検討し、残す内容・移動先や参照先への影響・未解決を示します。新しい自動保全・統合機構があるとは扱いません。

- 内容調査と保全案・影響・未解決を示した後、**「アップデートしますか？」と聞いて、その返答はそこで終えます。** 次の本人のOK後だけ、同じ旧版・抽出先・planでapplyします。未解決の競合があればOK後も適用せず、解決を待ちます。
- `--overwrite <名前>` は、保全方針が解決済みで、本人がその差分と置換に了承した標準ファイルだけに使います。ユーザースクリプトを消す手段や未解決の競合を押し切る指定にはしません。保全のための分離・統合を実際に行う場合も先に了承を得て、OS更新とは分けます。変更後はcheckし直し、最新の差分・planで確認します。
- 適用はワークスペースの信頼済み旧版で `python3 -I tools/update_os.py apply --from <確認済みの新しい版> --plan <checkの番号>`。確認後にbytesやmodeが変われば計画を取り直します。未検証の新版の道具を先に実行したり、製品ファイルの手コピーで適用を迂回したりしません。
- macOS・Windowsのapply前には「確認の窓が出るので、よければ『更新する』を押してください」と伝え、AIが信頼済み旧版のapplyを起動する。本人はコマンドを貼り付けず、別窓の対象・版・planを読んでボタンを押す。AIは窓を操作しない。Windowsは同じ対話デスクトップ上のWindows Pythonから、システムフォルダのWindows PowerShellと標準Windows Formsで表示する。VS Code内のボタンや拡張機能は使わず、PC設定・実行ポリシーも変更しない。既定は「やめる」で、閉じる・Escape・約2分の時間切れ・表示失敗では適用しない。表示失敗を端末入力で自動回避しない。
- WSL・SSH・コンテナ・非対話セッションでは手元のWindows確認窓を保証しない。実行場所を確かめ、Windowsの作業場をローカルWindows Pythonで開き直す。その他のOSでは本人が自分のターミナルでapplyを実行し、内容を読んで「更新する」と入力する。AIは端末入力を代行しない。閉じた・出せなかったときは実行結果を確認し、未適用ならその状態と再試行の選択肢を伝える。
- この確認窓機能をまだ持たない旧Windows版からの最初の更新は、旧版が持つ本人の端末入力で導入する。未検証の新版updaterを先に起動したり手コピーしたりして初回だけの入力を省かない。導入後の更新からWindows確認窓が使える。
- 本人だけの決まりは `wiki/me/profile.md` の「AIへのお願い」へ置く。AGENTS.md等の独自追記が上書き対象なら差分を示し、移すかを聞く。了承後にOS更新とは別のcommitで移す。`DESIGN.md` が独自編集されていたら止まって差分を説明し、黙って上書きしない。デザインの設定先は `tools/design.md`。
- 完了した更新の取消は、対象の更新commitを確認して `git revert` する。中断中は途中をcommitせず「中断・停止したとき」の旧版復旧処理を使う。
- 本人の確認窓を通しますが、書込権限を持つAIの自己承認を技術的に封じる機能ではありません。本人が「確認はいらない」と言っても窓は省略しません。
- Wiki本文、レシピ、独自スキル、projectsは更新しません。例外の `wiki/README.md` はOSの読み書き規則で、本人の変更があれば確認対象です。`tools/` はOS用、本人用の道具は `projects/` か `recipes/` へ置きます。
- 実機の動作確認はmacOSで行っています。Windows向けの互換処理と模擬試験はありますが、実Windowsの最終確認は未完了です。この通常Git tree経路の実環境受入れは別途確認が必要です。anchor未設定の旧版を会話中に直接書き換えて取得できるようにしてはいけません。
- 更新前に旧版の復旧処理と変更前bytes・mode・indexをgit領域へ保存します。更新前後のOSファイルのmodeは0644か0755に限定し、0600などは勝手に変更せず停止します（Gitで完全に取消できないため）。更新commitは対象だけを含みます。pre-commitの拒否は尊重しますが、承認内容を変えるhookは停止します。commit-msg・prepare-commit-msg・post-commitとcommit署名は実行しません。ref/indexのhookは動き得ます。hookによる任意の副作用は保護できません。Gitは `git hook run` に対応した版が必要です。

## 初回だけの導入

利用者のワークスペースは自身のGitで管理し、公式repoのGit履歴を混ぜたり既存の `.git` を取り替えたりしません。Gitがない場合の初期化・初期commitは、配布元・対象・除外を確認して本人の了承を得る別工程です。Git対象外ファイルはGitで戻せません。OS更新への了承を成果物コピー・独立Gitの新設・pushへの了承にしません。

この復旧機能がない古い版や、公式anchorが空で日付版だけを扱う試用版からは、そのまま通常fetchで移れません。[初回導入](setup.md)に従い、本人が公式URL・固定commitと検証器の内容を点検し、信頼を確立する一度だけの移行が必要です。「ZIPの外で受け取ること」自体は必須条件ではありません。既存ワークスペースへの適用は差分了承と本人確認を維持し、旧版の定数の手編集や製品ファイルの手コピーで迂回しません。案内・点検が不足していれば停止し、この候補を作っただけで既存ワークスペースへ適用済みとは扱いません。

## 公式リポジトリの通常Git treeから取得する

### まず公開tagだけで有無を確認する

ワークスペースのルートから信頼済み旧版で実行します。通常はrefを省略し、公式repoの `default_branch` を使います。本人が指定した場合は `--ref main`・安定tag・full commitを使えます。

```sh
python3 -I tools/release_package.py status --ws .
python3 -I tools/release_package.py status --ws . --ref <ref>
```

いずれかを実行します。statusは、認証なしのHTTPSで公式identity（owner/repo・数値ID・Public）を確認し、`git ls-remote` でrefをfull commitへ解決して、そのcommitを指す注釈つきの公開tag `vX.Y.Z` がちょうど1つあることを確かめます。版はそのtagの名前から得ます。ファイルは取得しません。JSONの `available`（true/false）・`current_version`・`version`・`commit`・`ref`・`release_tag` を返します。`available: false` は正常な「更新なし」です。そのcommitに公開tagがない場合、注釈つきの公開tagが複数ある場合、注釈のない公開tagが付いている場合と、通信の失敗は「未確認」と伝えます。

`available: true` なら、**fetchより先に「更新があります（現在の版 → 確認した版）。続けて内容を調べます」と本人に応答**し、その同じターンで次へ進みます。`available: false` なら「更新はありません」と返し、全tree取得やapplyは行いません。

### 更新があると応答した後、同じcommitの内容を調べる

```sh
python3 -I tools/release_package.py fetch --ref <statusのcommitのfull commit> --ws .
```

statusで解決したfull commitをそのまま使い、動くmain/tagを解決し直して別の内容を取得しません。fetch単体の契約は `fetch --ws <ws> [--ref <ref>]`、ref未指定は公式repoの `default_branch` です。既存互換の `--tag v4.0.1` も使えますが、通常のstatus後はfull commit固定の `--ref` を使います（`--ref` と `--tag` は併用しません）。例のtagは公開済みという意味ではありません。

必要な道具はGitとPython 3だけです。GitHub CLI（`gh`）とGitHubへのログインは要りません。公式リポジトリは公開なので、認証なしで読みます。トークンをAIへ貼り付ける場面はありません。通信先は `github.com` と `api.github.com` の2つです。

取得元は検証器に固定した `kote2kote/kote2-builder-ai-os`（数値ID `1435376611`）です。認証なしのHTTPSでowner/repo・数値ID・Publicであることを確認し、選んだrefを `git ls-remote` でfull commitへ解決します。そのcommitと、それを指す公開tagだけをHTTPSで隔離した一時bare Gitへfetchし、checkoutせずblobから配布内容を抽出します。取得した新版コードは実行しません。続けて**公開の記録を照合**します。公開tagの対象と名前、tagの本文にある `commit`・`tree`・`release-files.json sha256` の3行が、取得したcommit・そのtree・配布一覧のhashと一致しなければ停止します（公開作業で受け入れた版だけを取得するため）。専用配布ZIP・Release・attestationは必須ではありません。通信・取得・commit整合・公開の記録・内容検査のどれかが失敗すれば停止し、検査を省く指定はありません。同じ版・古い版も更新用fetchでは拒否します。

抽出先はワークスペース外の新規一時フォルダです。全配布inventory・ファイル集合・hash・mode・VERSIONとの一致と新しい版であることを検査した後、旧版 `update_os.py check` を呼びます。ref・解決したfull commit・版・抽出先・planを本人に示し、カスタマイズを残す案・影響・未解決を調べて「アップデートしますか？」で止まり、次のOK後だけ同じ抽出先とplanを使って上の旧版applyで本人確認します。未解決の競合は上書きしません。検証した新版の道具も更新前には実行しません。確認後に対象bytesやmodeが変わればapplyは停止します。一時フォルダが消えた場合はfetchからやり直します。

### 確認・取得ができないとき

道具は止まった理由を次のどれかで伝えます。どれも「未確認」で、「更新なし」ではありません。

- 「GitHubへ接続できません」: 通信が許可されていない、またはオフライン。AIの実行環境（sandboxなど）が通信を止めている場合を含みます。
- 「GitHubのTLS証明書を確認できません」: 証明書の検証に失敗。検証は省略しません。
- 「GitHubの応答が時間内に返りませんでした」「回数制限に達しました」: 時間をおいて確かめます。認証なしの確認は、同じ回線の合計で1時間に60回までです（1回の確認で1回、取得でもう1回使います）。解除までの目安が出たら、その時間を本人に伝えます。
- 「公開の記録を確認できません」: 公開tagが付いていない。公開作業の途中か、公開されていない変更です。取得しません。

このときAIは次を守ります。

- **sandboxなどの保護やTLS証明書の検証を、無効にしたり弱めたりする案を出さない。行わない。** 選択肢として並べることもしません。sandboxの外での再実行、検証を省く指定、別の入手経路（手コピー・ZIP・別のリポジトリ）での回避もしません。
- 本人には「確認できませんでした（理由）。更新なしという意味ではありません」と伝え、次のどちらかを案内します。
  1. **本人が自分のターミナルで、同じコマンドを実行する。** ワークスペースのフォルダで上の `status`、続けて `fetch --ref <statusのcommit>`。本人のターミナルのコマンドはAIのsandboxでは保護されないので、ここに書いてあるコマンドだけを実行してもらいます。出力は本人が先に読み、秘密や個人情報を除いてからAIへ渡します。AIは抽出先の内容と旧版checkの差分を読んで説明し、次のOKを待ちます。applyは本人の確認の窓を通します（AIから起動できなければ、本人が同じapplyコマンドを自分のターミナルで実行します）。
  2. **Claude Codeのsandboxを使っていて、通信先が許可されていない場合**は、通信先 `github.com` と `api.github.com` だけを許可する設定を、本人が選べば足せます（[設定手順](building/settings.md)）。既存のlocal設定を無断で変更せず、変更案を見せて了承を得ます。許可を足さない選択も尊重し、その場合は1を使います。
- 4.5.1以前の版に入っている道具はGitHub CLIを使い、Claude Codeのsandboxの中では確認も取得もできません。その版から更新するときは、1の方法（本人のターミナル）で行います。4.3.1〜4.5.1からは最新へ直接なので一度だけ、4.0.0〜4.3.0は4.3.2と最新の2段それぞれで行います。4.5.2以降が入れば、通信先を許可したsandboxの中でも確認・取得できます。

配布ルートの `release-files.json` は全配布ファイルの検査用で、利用者Wiki全体の同期用ではありません。`python3 -I tools/release_package.py inspect <配布フォルダ>` はGit履歴なしで内容を点検しますが、同梱hashだけでは真正性を証明できません。利用者の育ったワークスペースへこの検査をかける用途でもありません。この一覧自身はOS更新対象外で、初回の一覧がワークスペースに残っていても現在のWikiや更新状態を表しません。

`LICENSE`・`NOTICE`・`THIRD_PARTY.md`・`CONTRIBUTING.md` は配布物全体の検査に含めますが、通常のOS更新では同期しません。既存利用者は公式repoの取得した固定commitと版ごとの案内から、その版の条件を参照します。利用者Wiki・成果物・レシピ・法務文書を自動同期せず、AIがこれらを個人ワークスペースへ勝手にコピーすることはありません。

## 不具合や改善案を伝える

[不具合の報告手順](../CONTRIBUTING.md) に従い、本人が本文と宛先を確認した後だけIssuesへ伝えます。外部PRは受け付けません。自動収集や自動送信は行いません。

Wiki画面の3D/CMSは版と中身を固定した外部CDN（jsDelivr/unpkg）へ接続します。配布物内にその実行コードを同梱する方式ではなく、画面を開くと接続先にIPアドレスなどの通常の通信情報が伝わります。

この経路はGitHubの公式元から取得したこととcommit・配布内容の整合を確認しますが、従来の署名・attestationと同等の暗号的な配布者証明ではありません。同梱hashは自己申告でもあり、公式アカウントやrepoの侵害、配布者のコードの正しさ、試験の実施、Private正本とPublicの一致を証明するものではありません。公開者側の別点検が必要です。full-accessでの手動迂回や同権限プロセスの瞬間的競合まで防ぐ保証はありません。

## 中断・停止したとき

WindowsではJSON・Markdown等のファイル読書きにUTF-8を明示し、日本語・空白・長いパスやACL・所有者の違いを確認します。macOS用の確認窓や `open`・AppleScript・シェルスクリプトをそのまま実行しません。Gitの所有者不一致は [初回導入](setup.md) に従い、本人が了承したrepoのパス1件だけを必要な呼出しの `safe.directory` に指定します。`*` や無断の全体設定変更で回避せず、了承がなければ読取りと未確認の説明にとどめます。

表示されたgit領域の `builder-os-update/recover.py` を `python3 -I <表示されたパス> recover --ws <ワークスペース>` で起動します。新しい版の道具が壊れていても保存した旧版から起動できます。commit前は対象だけを戻し、成立済みの更新commitなら対象indexだけを整えます。本人の追加編集・別commit・不明なlockがあれば何も戻さず停止します。`reset --hard` は使いません。

停止が続くときは、AIは理由・HEAD・対象差分・対象indexを読み取りで示し、本人の判断を待ちます。別のGitが動いている間はlockを削除しません。lockの所有者が分からなければそのまま保留します。本人編集と復旧記録のbefore/expectedを確認して必要な内容を別途保全し、人が整合性を確かめた後だけ記録をgit領域の別名へ退避して再計画します。退避自体は復旧ではありません。記録の自動破棄・本人編集の上書きはしません。

`builder-os-update-prepare-*` だけが残った場合は、対象に書く前の準備中断です。正式記録とは別なので再計画できます。`builder-os-update-finished-*` は対象処理を確定した後の片付け残りです。どちらもワークスペースのファイルを戻すために使わず、人が内容を確認して片付けます。電源断、同権限プロセスとの瞬間的な競合、ACL/xattr/所有者の保存、git領域と対象が別ファイルシステムの構成は保証していません。

## 4.5.1と4.5.0の番号

4.5.2は4.5.1の次に公開する版です（更新の確認・取得をGitHub CLIなしにした版）。4.5.1は4.4.0の次にGitHubで公開した版です。4.5.0という番号は、一部の手元の作業場に入れた公開前の候補にだけ使い、GitHubには公開していません。その候補と公開版は中身が違うため、同じ4.5.0として配らず4.5.1にしました。

- 4.4.0・4.5.1の作業場: 通常の更新で最新へ進みます。途中の版は経由しません。
- 公開前の4.5.0が入った作業場: 通常の更新で最新へ進みます。4.5.0の再導入・同じ版の再適用はしません。
- 旧版（4.0.0〜4.3.0）: どのOSでも4.3.2→最新（4.5.2から、macOSなども4.3.2を経由します）。4.4.0・4.3.1は経由しません。
- すでに4.3.1の作業場: 最新へ直接進みます。
- 4.3.1〜4.5.1の作業場でClaude Codeのsandboxを使っている場合: 入っている道具はsandboxの中では確認・取得できないので、最新へ進むときだけ、上の「確認・取得ができないとき」の1（本人のターミナル）で行います。これらの版からは最新へ直接進むので1回です。4.0.0〜4.3.0は、下の2段階（先に4.3.2）のままです。本人が独自にsandboxを有効にしていて取得できない場合は、各段を同じように本人のターミナルで行います。

## 4.3.0以前から公式配置版への移行

**4.0.0〜4.3.0からの移行は、どのOSでも 4.3.2 → 最新 です**（4.5.2から。それまでmacOSなどは4.3.1経由でした）。4.3.2の中の説明（[移行の条件](windows-upgrade.md)）は「Windows向け」と書いてありますが、中身はどのOSでも同じ配布物で、macOSなどでもこの経路を使います。確認の窓まわりのWindows固有の注意は、Windowsだけに当てはまります。専用branch・完全commit・外付receiptを照合し、未公開ローカル候補を本番の取得先にしません。

4.3.1を新しく経由しない理由: 4.3.1の共有設定はClaude Codeのsandboxを必須にします。4.3.1に入っている道具はそのsandboxの中からGitHubへ届かないため、4.3.1を入れたあとでClaude Codeを起動し直すと、2段目の確認・取得がAIからできなくなります。

旧取得器はnativeパスを拒否するため、まず旧配置だけの移行版4.3.2、次に最新の公式配置版を検査・適用する。4.4.0は経由しない。各段階で導入済みの信頼済み道具と既存の確認窓を使う。最新を拒否されても、新版コードを先に動かしたり手コピーして回避しない。

4.3.2のpublic完全commitは `e1474089163b40c4cd3b0ea93d27ccd717b2746f`（専用branch `transition/4.3.2-windows`。mainには入らない）。取得不能なら停止し、検査を迂回しない。

1. 作業場の導入済み旧版で `python3 -I tools/release_package.py fetch --ref e1474089163b40c4cd3b0ea93d27ccd717b2746f --ws .`。返された4.3.2の抽出先・plan・差分・カスタマイズの保全案を確認する。取得結果の `commit` と `inventory_sha256` を、最新のReleaseに添付されたreceiptの `transition_windows` の値と照合する。
2. 「アップデートしますか？」への本人のOKを待つ。OK後、同じ旧版で `python3 -I tools/update_os.py apply --from <確認した抽出先> --ws . --plan <確認したplan>` を起動し、本人が正式確認窓で承認する。未解決の競合では適用しない。
3. 4.3.2の導入後、本人に依頼を言い直してもらわず、同じ依頼の続きとして、更新済みの信頼済み道具で `python3 -I tools/release_package.py status --ws .`。確認した最新の完全commitを `python3 -I tools/release_package.py fetch --ref <statusで確認した完全commit> --ws .` へ渡す。
4. 2段階目も差分と保全案を確認し、取得結果の `commit` と `inventory_sha256` をreceiptの `latest` の値と照合し、本人のOK・正式確認窓を別に通す。

**すでに4.3.1の作業場**は、最新へ直接進む（中継は不要）。4.3.1の共有設定のsandboxの中では確認・取得ができないので、上の「確認・取得ができないとき」の1（本人のターミナル）で行う。この更新で共有設定からsandboxの必須設定が外れるため、適用前に、本人の環境別local設定などで保護が続くことを確認する。未確認なら停止し、本人固有設定を上書きしない。更新後はClaude Codeを起動し直し、選んだ保護が効いていることを確かめる。

旧版の実装・独自編集によっては停止する。4.1.xすべての構成を一律保証するものではない。配布候補の道具を先に実行せず、各段階の取得・旧版check・本人確認を省略しない。

旧版で直接編集したAGENTS/settingsは最初の準備版更新でも競合する場合がある。止まった内容を消さず、具体的な保存・統合案を提示する。未解決のまま `--overwrite` しない。準備版以降はAGENTS利用者区画、JSONの追加キーと安全規則、保全可能なTOML追記を保持する。同じキーの衝突は停止する。Wiki・独自Skill・rules・local設定は更新対象外。旧tools/skillsの残った資産は勝手に削除しない。

本人の恒常設定は `tools/ai-preferences.md` に従い、Wikiの希望とネイティブ指示へ反映する。Wikiだけに置いて設定更新を避ける運用から移る。
