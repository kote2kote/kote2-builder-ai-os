# 初回導入と環境の確認

[READMEへ戻る](../README.md)

公開リポジトリから初めて導入するときに、配布物と環境を確認する手順です。公開済みであることは、すべての環境での動作や成果を保証しません。[第三者素材の条件](../THIRD_PARTY.md)を確認してください。専用ZIP・タグ・Release・attestationの発行は通常の導入・更新の必須条件ではありません。

## 公式の配布元とバージョン

- 公式リポジトリ: [kote2kote/kote2-builder-ai-os](https://github.com/kote2kote/kote2-builder-ai-os)
- リポジトリの数値ID: `1435376611`。名前だけでなく、このIDとPublicであることも確認します。
- この配布物の版: ルートの [`VERSION`](../VERSION) が正本です。導入記録には取得したcommitと併せて残します。
- 修正はpatch、互換性を保つ機能追加はminor、互換性のない変更はmajorを進めます。同じ版の配布物は後から差し替えません。

必要な道具はGit・Python 3と、更新元のAPI確認に使うGitHub CLI（`gh`）です。安全性を確認した公式版を使ってください。通常Git tree取得はRelease検証を使わないため、Release検証用の `gh 2.102.0` 最低版条件はありません。API利用に認証が必要なら本人が設定し、トークンをAIへ貼り付けません。

全機能の利用には **Python 3.11以上を推奨**します。とくに `tools/building_check.py` の **Codex設定検査はPython 3.11以上が必須**です（`tomllib`を使用）。`python3 --version`で確認してください。Windowsで `python3` がなければ `py -3 --version` で確認し、以降の例もその起動方法に読み替えます。古いPythonですべてのCLIを一律停止する規則ではありません。必要な機能の条件に合わせて本人が準備し、AIはPythonや既存CLI設定を自動で入れ替えません。macOSでの確認実績はありますが、実Windowsの最終確認は未完了です。

AIはワークスペースまたは案件のルートで開始し、[AI別の設定と権限](building/settings.md)で読み込まれた設定を確認します。Claudeの秘密ファイル規則とCodexのサンドボックスは範囲が異なり、設定だけで秘密を完全隔離するものではありません。既存のカスタム設定を保持し、ホーム設定や認証を上書きしません。

## 初回の信頼を人が確認する

検証器がまだない最初の導入では、**公式URL・数値ID・取得するfull commitと、そのcommitの内容を人が確認します。** 検索結果・同名repo・「最新」という表示や、配布物に同梱されたhashだけでは取得元を信用しません。「ZIPの外から検証器を受け取ること」自体は必須条件ではなく、確認した公式元・固定commitと検証器の内容点検を信頼の起点にします。

1. すでに信頼している配布者の案内から公式URLを確かめ、GitHub上のowner/repo・数値ID・Publicであることを照合します。確認できなければ導入を止めて問い合わせます。
2. 公式repoの内容を確認し、導入対象をfull commitへ固定します。default_branchやmain、安定tagから選ぶ場合も、動く参照名だけではなく、その時点のfull commitを記録します。
3. 「Use this template」で自分専用のPrivateリポジトリを作るか、確認用cloneから配布ファイルだけを別の新規フォルダへ取り出し、そこで独立した `git init` を行います。公式cloneの `.git` は確認用フォルダに残し、仕事用フォルダへ持ち込みません。選んだ固定commitとの内容一致を点検し、ボタンを押すだけで信頼確認を済ませません。作成までに参照先が変わった場合は止めて確認し直します。既存利用者repoの `.git` を削除・差替えして独立化する手順ではありません。
4. `AGENTS.md`・検証器 `tools/release_package.py`・更新器 `tools/update_os.py` を含む内容を、AIで開いたり実行したりする前に人が点検します。信頼を確立した検証器の `inspect <配布フォルダ>` で全ファイル集合・inventory・hash・mode・版を確認します。未知の検証器で自己検証しただけでは信頼確認になりません。
5. 公式URL・数値ID・full commit・VERSION・検証器の確認内容と検査結果を導入記録に残します。確認が終わってから[READMEの「Getting started」](../README.md#getting-started)へ進みます。仕事の記録は自分専用の独立したPrivateリポジトリで管理します。

この経路はGitHubの公式元とcommit・配布内容の整合を確認するものです。従来の署名・attestationと同等の暗号的な配布者証明ではなく、公式アカウントやrepoの侵害、コードの安全性、試験の実施を保証しません。初回の内容点検や公開者側の権利・秘密点検の代わりにはなりません。

## 導入後の履歴と更新

公式リポジトリを直接仕事場として使ったり、公式元の `git pull` で仕事用フォルダを更新したりしません。配布元履歴と利用者の独立Private履歴を分け、通常更新は[OSの更新・取消・復旧](os-update.md)の信頼済み旧版によるstatus → 「ある／なし」を返答 → ある場合は同じターンで固定commitのfetch・check → カスタマイズを残す案と影響・未解決の提示 → 「アップデートしますか？」で停止 → 次のOK後に本人の確認の窓でapplyを使います。最初の「更新して」は調査開始の依頼であり、適用承認ではありません。API確認に失敗した場合は「未確認」とし、未解決の競合は上書きせず停止します。利用者Wiki・成果物・レシピ・法務文書を自動同期しません。

## Windowsで履歴保存が止まるとき

- `detected dubious ownership` は所有者と利用者の不一致によるGitの停止です。Wikiへの書込みとGitの履歴保存は別に報告します。まず自分のアカウントで展開したフォルダか確認し、必要ならそのフォルダだけを信頼する案を本人へ示します。AIは `safe.directory=*` やPC全体の信頼設定を勝手に変えません。
- Gitの改行変換でOSファイルのbytesが変わると、配布hashと一致しなくなります。初回の履歴保存前に `git config --show-origin --get core.autocrlf` で設定を確認し、必要なら、このワークスペースだけ `git config --local core.autocrlf false` にする案を説明して了承を得ます。全体設定や既存ファイルの一括改行変換はしません。既にCRLFになったファイルを「同じ」と扱ったり、検査を省略したりしません。

両コマンドはこのワークスペースのルートで使います。Gitの所有者エラーがある間は先にその確認を行い、設定に失敗したのに完了と報告しません。

所有者が違う場合も自動で信頼を広げません。本人が今回のフォルダを確認して了承した場合だけ、対象の絶対パス1件を `git -c safe.directory=<確認したフォルダ> ...` でそのGit呼出しに限って指定できます。これは所有者やPC全体の設定を変えず、子プロセスに自動では引き継がれません。移行ツール内のGitにも必要なら、既存の `GIT_CONFIG_COUNT` とその設定を壊さない実行中限定の環境設定を使い、終了時に戻します。ワイルドカードや無関係なフォルダは指定しません。了承がなければ履歴保存・適用は止め、読取り可能な調査と未保存の説明にとどめます。
