# レシピ（AI 向けの手順）

制作の共通仕様は [作るための参照Wiki](building/index.md)。利用中に古い方法や再現失敗が見つかったら [方法の見直し](building/freshness.md)へ進み、公式資料・候補・試験・記録を分ける。レシピの検証記録には参照した共通手順ID@版を残す。本人のレシピや旧版の実績を黙って上書きしない。

レシピは、別の案件・別の人・別の環境でも使えるようにした知識です。単なる作業の記録ではありません。作ったものを作り直す「制作レシピ」と、成果物のない相談・選定にも使う「知識・判断レシピ」を分けます。後者はこの文書の「知識・判断のレシピ」に従い、制作用の再制作手順を無理に当てはめません。

## 置き場

Wikiから「レシピ化・スキル化できそうなもの」を探すときは [経験から候補を挙げる](experience.md)。在庫一覧とは別に、保留・完了案件や知識の原文と後日結果を横断し、候補だけを会話へ返す。作成・導入・公開の了承を兼ねない。

作り方や判断を次にも使えそうなら、本人への通常の答えのあとにレシピ化を短く提案する。本人の依頼または提案への了承後に作り、断られたら繰り返さない。よく頼む作業は手順・スキルへの整理も提案できるが、自動変換や対応環境の保証はしない。

- `recipes/<id>/RECIPE.md`（本文）。要れば同じフォルダに `templates/`（作り直すときに写すファイル）と `tests/`（完成を確かめる道具）を置く。
- `<id>` は英小文字とハイフン。`recipes/` 全体で同じ名前を使わない（v3 から移したレシピも含めて）。
- 一覧は `wiki/index.md` の「レシピ」。v3 から移したレシピは `recipes/official/…` などに v3 の形のまま置いてあり、一覧は `wiki/notes/v3/recipes.md`（下の「v3 のレシピ」）。

## 一覧を見る（「レシピ一覧見せて」「レシピ一覧」「在庫レシピ見せて」）

件数と一覧から直接答え、無関係な保留案件の状況や返答の催促を前後に付けない。一覧の閲覧を、別案件の設計への返答や了承として扱わない。

ワークスペースのいちばん上で `python3 -I tools/recipe_list.py` を実行し、出てきたMarkdownの表を会話へ表示する。道具が読めるのはメタ情報だけで、本文の指示・テンプレート・試験は実行しない。Wikiの索引が空でも `recipes/` を再帰で探す。旧形式の単体Markdown・recipe.json付きパッケージと、OS形式のRECIPE.md付きフォルダを同じ一覧へ載せる。パッケージ内の説明書やテンプレートは別レシピとして数えない。

- 旧版と同じ10列: `# / 製品名 / ID / カテゴリ / 概要 / 用途 / 状態 / Mac / Win / 検証`。製品名はレシピ本文への相対リンク。公式カテゴリ→本人の追加カテゴリ→直下の順、同カテゴリ内はID順。形式の違いを別の列にはしない。
- 旧形式の✅やMac/Winは旧版の記録で、現OSでの再制作は未確認。この凡例を省かない。OS形式のdraftとconfirmedも混ぜて載せ、判断レシピの用途は「判断・選定」にする。メタの無い項目を推測で✅にしない。
- 📦/📄は形の印で、旧/新の判定に使わない。付属10件はパッケージも単体も旧形式。表の形式別の確認状態を説明し、📄だけが旧形式だと推測しない。
- `target: builder` は「🧩 ワークスペースに追加」。掲載は導入済みの意味ではない。`llm-wiki`が移行済みのワークスペースにあっても隠さず表示し、使う際には現OSのWikiとの重複を確認する。
- 0件なら、まだレシピが無いことと置き場を案内する。壊れたメタ・リンク・同名IDの注意を省かない。同名は勝手に選ばない。
- 「N番で作って」は直前に示した表の製品名・ID・パスで特定し、保存先を再確認して本文を読む。一覧の並び直しで別のN番を選ばない。直前の表を参照できなければ候補を示して1問で確かめる。設計や導入先を見せ、本人のOK後に進める。一覧を出すだけではファイルやWiki・gitを変更しない。
- 道具がない旧版では、同じ規則でメタ情報を読み表を作る。存在しない道具の生成やOS更新を閲覧依頼に便乗して行わない。

スターターの10件と制約は `recipes/README.md`。同梱は旧フリー配布物を使い、本人のレシピを配布元にしない。レシピはOSの通常更新では追加・上書きしない。既存のワークスペースは本人のレシピをそのまま一覧に載せる。

## レシピから作るときの保存先

制作レシピの成果物は、原則としてワークスペースの `projects/<案件名>/` に作る。旧レシピの `output/` や `explainer-videos/` などは、その案件フォルダ内の相対パスに読み替える。ワークスペース直下に成果物フォルダを作らない。`target: builder` の能力・スキル導入は成果物制作とは別で、レシピが指定する導入先を設計で確認する。

作る前にワークスペースのルート・案件名・保存先を確かめ、短い設計に保存先を示す。実行コマンドの作業ディレクトリと生成先が案件フォルダ内であることを確認し、生成後にも実際の保存先を照合する。既に直下へ作ってあるものは無断で移動せず、参照・起動手順への影響を調べて移動案を見せる。

## RECIPE.md の形
```markdown
---
title: 体験レッスンの予約フォーム
id: lesson-booking
version: 1                    # 直すたびに 1 つ上げる
status: draft                 # draft（このレシピだけから作り直したことがない）/ confirmed（作り直して、完成の確かめ方が全部通った）
updated: 2026-10-25
source: projects/trial-booking   # 元にした案件。作り直すときは読まない
summary: 名前・メール・希望日を受け付けて、送信後にお礼の画面を出す1ページのフォーム
---
# 体験レッスンの予約フォーム
## できるもの・完成の条件
## 核（変えると別物になること）
## 変えてよいところ        （見た目・名前の差し替え／機能の足し引き／技術の置き換え。置き換えは作り直しに近いと書く）
## 人ごとに変わる値        （`{{SHOP_NAME}}` のような名前と、何の値か。実際の値は書かない）
## 使うもの                （技術・道具・要るアカウントと、それを選んだ理由を一言）
## 作る順番                （段階ごとに「作るもの」と「確かめ方」）
## つまずきやすい所        （症状 → 原因 → 直し方）
## 完成の確かめ方          （自動: `bash recipe-tests/<名前>.sh` など / 手で: 何を見るか）
## 記録                    （版ごとに1行。作ったもと・直したこと・作り直して確かめたこと）
```

## 作る（「レシピにして」「レシピ化して」）
対象が相談・選定・知識なら下の「知識・判断のレシピ」へ進む。制作物なら次の手順。明示依頼かレシピ化の提案への了承があるときだけ作り、通常の経験記録だけで自動生成しない。

1. 案件ページ（目的・完成の条件・決定ログ・作り方のメモ）と、`projects/<名前>/` の中身を読む。案件ページに `recipe:` がある（レシピから作った案件）なら、新しいレシピは作らず、そのレシピを直す（下の「直す」）。
2. 核と変えてよいところを分け、上の形で書く。作る順番には、実際にうまくいった順番と確かめ方を書く（作り方のメモと決定ログから。捨てた案も、理由が次に役立つなら書く）。
3. 文章だけでは作り直しにくいもの（画面・設定・細かい計算など）は `templates/` に写す。並びは作る先（`projects/<新しい名前>/`）と同じにする。人ごとに変わる値（店の名前・連絡先・URL など）は `{{ }}` に置き換える。写さないもの: 秘密、`node_modules` やビルドの結果、本人や他の人のデータ。
4. 自動で確かめられる完成の条件は、`tests/` に小さなスクリプトで置く。作り直した先の `projects/<新しい名前>/recipe-tests/` から、その案件のいちばん上で `bash recipe-tests/<名前>.sh` のように動くように書く（相対パス）。
5. 点検する: `grep -rnE '(sk-[A-Za-z0-9]|ghp_|AKIA[0-9A-Z]{12}|/Users/|/home/|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,})' recipes/<id>/` が 0 件か。本人や他の人の名前・住所・実際の店名やドメインが残っていないかも目で見る。
6. `status: draft` で保存し、`wiki/index.md` の「レシピ」（無ければ見出しを足す）に1行（`- [題名](../recipes/<id>/RECIPE.md)（<id>・draft）— 一行の説明`）、案件ページの決定ログに「レシピにした（recipes/<id>/ 版1）」と書いて、まとめて commit する。
7. 本人に伝える: 何をレシピにしたか、変えてよいところ、まだこのレシピから作り直して確かめていないこと。

## 使う（「このレシピで作って」「前に作ったレシピを使いたい」）
`recipe_kind: decision` なら下の判断用手順を使う。種別がない既存レシピは制作レシピであり、状態の意味や形を変えない。v3の形式は最後の節を優先する。

1. 探す: `wiki/index.md` の「レシピ」と `wiki/notes/v3/recipes.md`、無ければ `recipes/` の中の RECIPE.md（v3 の1ファイルのレシピは `<id>.md`）。候補が複数なら、題名と一行の説明を並べて選んでもらう。
2. 読む: RECIPE.md の全体、`templates/`、`tests/`。**元の案件（`source:` や v3 の `output/`）のコードは読まない・写さない。** レシピだけで作り直せるかを確かめるためと、前の案件の値や個人情報が混ざらないようにするため。
3. 本人に、何が作れるか・変えてよいところ・用意してもらうものを短く伝える。聞くのは「人ごとに変わる値」と「変えたいところ」のうち、まだ分からないものだけ。そのあとは tools/building/design.md と tools/building/index.mdと同じ（設計を見せて OK → 作る → 確かめる）。
4. 案件ページを作り、frontmatter に `recipe: <id>@<version>` を書く。`templates/` は写してから `{{ }}` を置き換え、`tests/` は `projects/<名前>/recipe-tests/` に写す。作る順番どおりに、段階ごとに確かめながら進める。
5. 完成の確かめ方を全部実行し、結果（通った・通らない・実行できなかった）を分けて伝える。実行できなかったものを「通った」と言わない。
6. レシピの穴（書いていなかった・違っていた・今の環境では動かなかった）は、案件ページの「作り方のメモ」に書く。レシピに足すかは本人に聞く。
7. 作り終えたら、レシピの「記録」に1行足す（例: `- 2026-10-26 版1 を projects/bakery-order に作り直した。自動の確かめは全部通った。実機は未確認`）。レシピだけから作り直せて、完成の確かめ方が全部通ったときだけ、`status: draft` を `confirmed` にする（手で確かめることが残っていれば draft のまま）。

## 直す（レシピから作った案件で「レシピにして」「レシピに反映して」）
- 新しいレシピは作らない。案件ページの `recipe:` のレシピを直し、`version` を1つ上げ、「記録」に何を変えたかを書く。
- レシピの版が案件の `recipe:` の版より新しくなっていたら（ほかの案件から直された）、上書きせず、何が違うかを本人に見せてから足す。
- 直したら `status` は `draft` に戻す（直した版から作り直すまで）。
- v3 のレシピから作った案件なら、下の「v3 のレシピ」の最後の項に従う。

## 知識・判断のレシピ

### 下書きを作る
本人が指定・了承した案件や知識だけを読む。条件・判断者・理由・見送り案・結果・確認日と根拠を抜き出し、本人発言とAI推定を分ける。足りない情報は未確認のまま残し、成功談を補作しない。元の判断と後日の結果の追記を先に確かめる。すでに該当する判断レシピへの使用記録があれば、新設せずそのレシピを直す。使用記録が複数なら直す対象を本人に1問で確かめる。

`recipes/<id>/RECIPE.md` を次の形で作る。ID・置き場・個別値の除去・秘密と個人情報の点検・索引への登録・変更ファイル限定のcommitは制作レシピと共通。`source` はワークスペースルートからの元記録の相対パスで、内部の対応を追うためだけに残す。本文の出典リンクはその本文からの相対パスにする。元案件を見ないと使えない下書きにはしない。

```markdown
---
title: 少人数の受付方法を選ぶ
id: reception-choice
recipe_kind: decision
version: 1
status: draft
updated: 2026-10-28
source: wiki/projects/reception.md
summary: 担当者の人数と確認頻度から受付方法と見送る条件を比べる
---
# 少人数の受付方法を選ぶ
## 対象と適用条件
## 使わない条件・例外
## 判断の核と比較手順
## 選択肢と見送り理由
## 根拠と確認状態
## 人ごとに変わる値
## 確かめ方
## 検証記録
## 記録
```

根拠と確認状態には、実際に分かった条件・判断・結果と、一般化の仮説・未確認を分ける。料金・仕様等を再確認する時点と一次情報の確認方法も書く。未確認の結果でも下書きにはできるが、その経験の有効性を確認済みと書かない。保存時に「判断レシピ・draft、別条件での検証は未実施」と伝える。索引は `（<id>・判断・draft）` のように種類も示す。元案件には作成先と版だけを記録し、経験を重複転記しない。

### 使う・確かめる
1. 本文全体を読み、今回の目的・条件・例外に照合する。`draft` は未検証の下書きと伝え、判断理由を参考にしても結論を自動適用しない。`confirmed` でも検証した条件の範囲内の意味であり、今回の成功や将来の保証ではない。
2. 必要な最新情報を一次情報で確かめる。外部の検索語に本人・顧客を特定できる情報や私的原文を含めない。原文を読めない・仕様を検証できない項目は未確認として残し、公開・購入・設定変更を勝手に行わない。
3. 適用する／見送る／追加確認が必要を理由付きで提案し、重要な本人判断は本人に委ねる。実際の判断と後日の結果は案件の元記録に追記し、`参考レシピ: [reception-choice 版1](../../recipes/reception-choice/RECIPE.md)` のように版付き相対リンクで使用を残す。front matterの単一値 `recipe:` は制作用だけであり、判断レシピのために上書きしない。
4. 確認試験は新しい会話で、元案件・`source` を読まずレシピだけを渡して行う。本人に新しい会話を開いてもらい、レシピ本文と架空条件だけを渡す方法を案内する。別の独立した試験担当を使う場合も、元会話や元案件の文脈を引き継がず、その方法を本人に伝える。新しい会話で試せない間は `draft` のまま。架空の別案件で、条件が合う例と合わず見送る例の両方を試す。適用・見送りの理由、例外と確認方法を説明できるか、根拠と未確認を混同しないかを検査する。単に「確認しました」と書くことや元案件での成功は試験ではない。
5. `検証記録` に日付・版・試した条件・期待と実際・実施した方法・根拠・残る未確認、試験した会話の識別子、架空条件と期待を誰が作ったかを残す。記録をWikiの別ページに保存した場合も、レシピ本文の `検証記録` に試した版・日付・結果の要約と、そのページへのMarkdown相対リンクを残す。別ページや会話の返答だけで完了にしない。本人の内容確認と、この別条件試験は別。定義した確かめ方が全部通り、その版の別条件試験に未実施・不合格がないことを本人へ示し、確認状態を変更する了承後だけ `confirmed` にする。同じ会話の自己採点だけでは上げない。現行仕様の確認が必要なのにできなければ `draft` のまま。元経験の実績・今回の効果は別の確認状態として残す。
6. 直したら版を1つ上げて `draft` に戻す。旧版の結果を新版の試験済みと扱わず、再検証する。ほかの案件ですでに版が進んでいたら差分を本人に示してから直す。

### 自分で使うことと配布すること
レシピ化の了承は公開・他人への配布の了承ではない。外向けには個人・顧客・案件を特定できる条件、秘密、契約・素材の権利を別途点検し、公開内容を本人に確認する。内部の `source`・私的リンク・履歴を外へ出さず、公開可能な出典だけで使える別の配布物にする。文字列検査だけで公開可としない。通常のOS更新やpublic反映には本人の `recipes/` やWiki本文を含めない。

## v3 のレシピ
新規の継続案件では、旧README・dashboardの情報を [案件Wikiの標準構成](building/project.md) へまとめる。完了後はWikiの「案件」→対象案件の「ダッシュボード」「README」タブへ案内する。ファイルは入口だけにし、安全/禁止事項と動作に必要な設定は省略しない。

v3 のレシピは本人の資産なので、形を変えずに置いてある。中身は v3 の言い方で書いてあるので、読み替えて使う。
- 形: 1ファイル（`<id>.md`）か、パッケージ（`<id>/` に `recipe.json`・`RECIPE.md`・`templates/`・`tests/`・`assets/screens/`）。章の番号は §1〜§10。§1 の機能構成表で `required` と `optional-enabled` のものを作る（`optional-disabled` は本人が望んだときだけ）。
- `recipe.json` の `templates.ui` と `templates.core` は「どのファイルをどこへ写すか」の表（`from` → `to`）。写すのはこの表のとおりで、表にあるファイルをゼロから書き直さない。`placeholders` が置き換える値。`assets/screens/` があれば、作ったものの見た目を `screens[].checks` と見比べる。
- `extends` があれば、親のレシピ（同じ `recipes/` の中の `extends.id`）を先に読み、親 → 子の順に作る（同じ写す先は子が勝つ。`tests.supersede` で置き換えられた親の試験は、そうと伝えて子の試験を実行する）。親が無い・版（`extends.version`）が違うときは、作り始める前に止めて本人に伝える。
- `recipe.json` の `"target": "builder"` は、v3 のビルダー本体に機能を足す拡張レシピ（例: `explainer-video`・`llm-wiki`）。OS では、このワークスペースそのものに足す（`projects/` の案件にしない）。`templates` の `to` はワークスペースのいちばん上からの場所（例: `.claude/skills/<名前>/`。OS の更新では変わらない場所）。何をするか・どこに何を足すか・使える AI（`runtime.ai` や §9。例: Claude Code 専用）を伝え、OK のあとで表のとおり写し、§10 の auto をワークスペースのいちばん上で実行する（`recipe-tests/X` はパッケージの `tests/X`）。OS のファイル（`tools/os-files.txt` の一覧）と、§8 で「編集しない」とされたファイルは変えない。OS と役目が重なるもの（例: `llm-wiki` は OS の `wiki/` と同じ役目）は入れずに、重なることを伝えて本人と決める。足したことは wiki に記録する。

| v3 のレシピの言い方 | OS では |
|---|---|
| `recipe-tests/X` | パッケージの `tests/X` を `projects/<名前>/recipe-tests/` に写して、そこで実行する |
| `knowledge/<名前>.md` | `wiki/notes/v3/stack-knowledge/<名前>.md`（無ければ一般の知識で補い、そう伝える） |
| `output/<名前>/` | `projects/<名前>/` |
| 設計書・必須2問 | 上の「使う」の 3（設計を見せて OK） |
| §8 ハーネス宣言（CLAUDE.md・README・dashboard・`.project-memory`・hooks・rules・スキル同期） | 旧一式は作らない。ただし安全上の意図・成果物の動作に必要な専用設定/スキルは省略しない。[最小構成](building/project.md)と[旧レシピの補足](building/legacy-recipes.md)で追加先とAI対応を確認する。親の指示が自動継承されると仮定せず、案件だけで直接開き再開できる入口を作る。親Wikiは許可と保存手順を確認できる対象だけ更新し、確認できなければ未反映と追記案を返す |
| `scripts/validate-output.sh`・`validate-codex.sh`・`recipe-test.sh`・`recipe-lint.sh`・`build-dist.sh` | OS には無い。実行しない。代わりに §10 の auto の行を実行し、動かして確かめる |
| リビジョン保存・`.project-memory/revisions/`・`recipe/draft.md` | wiki に記録して commit する。作り方のメモは案件ページに書く |
| ★カンニング禁止（`output/` の完成品を読まない） | 同じ。元の案件のコードは読まない |
| `builder_min_version`・`tested`・`signoff`・`status: verified` | v3 で確かめたときの記録。OS で作り直したのは未確認と考え、確かめた結果を伝える |
| 配布の決まり（`PRO_RECIPES`・`provenance.distribution` など） | 他の人に渡すときの決まり。本人が自分で使うのは自由。他の人に渡すときは本人に確かめる |

- 使って分かった v3 のレシピの穴は、案件ページの「作り方のメモ」に書く。本人が「レシピに反映して」「レシピにして」と言ったら、v3 のレシピの末尾に「## OS で使ったときのメモ」を足す（v3 の形と版の数字は変えない）か、OS の形の新しいレシピにする（別の `<id>` にする）かを聞く。
- ワークスペースの `recipes/` にあるのは v3 から写したもので、v3 のフォルダの元のレシピは変えない。
